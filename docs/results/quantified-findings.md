# NetZoo agent：可量化的結果與其成立條件

本文只收「有數字、有可否證判準、判準在量測之前寫下」的結果。
每一項都註明證據來源（研究記錄 Log 編號、報告檔）與**不能宣稱什麼**。

環境：`gpt-4o-mini`（temperature 0）經 OpenRouter；離線與執行層閘門為本機 Docker，
映像 `netzoo_agent:latest`。語料 27 題，`corpus_sha256=a43c2baec7…`。

## 1. 量測方法與其限度

### 1.1 同碼替身輪：這個評估的解析度

**設計**：同一份程式碼、同一份語料、同一組參數，跑兩輪（各 81 次試驗＝27 題 × 3 次）。

**結果**（Log 98）：

| 指標 | r25 | r26 | 差 |
| --- | --- | --- | --- |
| 工具正確 | 21 | 22 | 1 |
| `passed` | 18 | 21 | **3** |
| 有被接受 outcome 的試驗 | 58 | 54 | **4** |
| 逐題計數不同的題數 | — | — | **6 / 27** |

其中 `covariate-coexpression` 在**零程式改動**下由 1 跳到 3。

**可引用的結論**：在 n = 81 的單輪下，**≤3 的差異無法與抽樣噪音區分**。
這條在本研究內部被實際觸發過一次——一條事前判準（「工具正確不得下降」）因
22 → 21 而踩線，替身輪回到 22，證明那是噪音（Log 97／98）。

### 1.2 結構性計數器 vs 分數指標

同一批資料裡，**程式後果型**的計數在替身之間完全一致：
`unmatched` 60 → 0 → 0、`without_span` 10 → 0、走某條程式路徑的次數 3 → 0 → 0。
而**分數型**指標（pass rate）被抽樣支配。

**建議**：agent 評估應報告結構性計數器；分數只能在差異遠大於替身離散時使用。

### 1.3 matched-control replay：把模型變異移除

**設計**：固定模型的第一次輸出（重建一個只有指定缺陷的解讀），只變動程式碼，
量第二次呼叫的修復率。模型仍真實參與修復，但第一次呼叫不再是變異來源。

**離散對照**：四次量測的逐輪離散為 **1／0／3／1**，對照全語料輪次的 ±3～±4。
**固定第一次呼叫之後，n = 36 就足以分辨 3 的差異；全語料 n = 81 分不出。**
本研究**所有**顯著結果都出自此設計
（0/33 → 16/33、p = 0.0011；2/36 → 22/36 → 35/36、p = 5.3×10⁻¹⁷），
**全語料輪次從未達到顯著。**

## 2. 發現：語料組成決定了結論（Log 93）

同一個系統、同一個度量，只因語料是否包含真實使用者條件而反轉：

| 引文失敗形狀 | 舊語料（20 題，35 輪，789 次試驗） | 新語料（27 題，r21，81 次試驗） |
| --- | --- | --- |
| `absent`（宣告有引文卻沒給） | **185** | 10 |
| `unmatched`（給了但原文沒有） | **3** | **80** |

**成因**：舊語料 20 題**每題拼字正確、每題都陳述自己有哪些輸入**。
`unmatched` 需要錯字或改述才會出現；語料裡沒有這個條件，就量不到這個現象。
新增 `misspelling` 與 `terse` 兩類（7 題）後比例反轉。

**後果可量測**：依舊語料排出的修復優先順序是**錯的**。
被判定「只值 3 筆」的介入（拼字軸對齊）實際上是最大的單一損失來源
（80 筆，且 `misspelling` 類 12 次試驗全損）。

**可引用的結論**：benchmark 若不含某條件，該條件的失敗率不是「低」，而是**未定義**；
而由此得出的優先順序可以完全相反。

## 3. 發現：契約允許了自己必然拒絕的形狀（Log 92／93）

**缺陷**：證據項的 `source="explicit"` 語意上要求引文，但送給模型的 JSON schema
把 `text_span` 標為 optional 且 `default: null`；要求只寫在 prompt 散文裡。
**模型跟隨 schema。** 驗證層隨後必然拒絕該形狀。

**規模**：35 輪、789 次試驗中，該形狀佔最大 issue 家族的 **185/188（98.4%）**，
且其中 **79%（148/188）** 導致**整輪解讀被丟棄**，而非只損失一個欄位。

**修正與量測**（r21 → r23，同語料）：

| | 收緊前 | 收緊後 |
| --- | --- | --- |
| 有被接受 outcome 的試驗 | 42 | **53** |
| `without_span` 條目 | 10 | **0** |
| `schema_validation` 試驗數 | 17 | **11** |
| 推薦錯工具／forbidden／unsafe | 0／0／0 | **0／0／0** |

**與直覺相反的部分**：把要求寫進 schema 之後 **schema 失敗變少了**。
機制是模型不再產出那個「之後必然被拒」的形狀，因此不必在第二次呼叫重寫整份結構。

**可引用的結論**：契約與其對外 schema 之間的不一致，會被模型解讀為「schema 為準」；
把約束只寫在自然語言指示裡，等於沒有約束。

## 4. 發現：一個可重現的 provider 行為缺陷（Log 93）

把「`explicit` 必須帶引文」寫成 JSON Schema 的 `anyOf` 兩分支時，
若分支只列出**受約束的屬性**、其餘靠與 root 的 AND 組合——
**這在 JSON Schema 語意上是正確的**——provider 會把分支當成物件的**完整定義**。

**後果**：模型回傳的證據物件只含 `source` 與 `text_span` 兩欄，
`dimension`／`value`／`rationale` 全部消失，**81/81 次試驗全部 schema 失敗**
（接受數由 42 崩到 2）。

**修正**：每個分支重述全部 required 屬性。修正後即為第 3 節的結果。

**可引用的結論**：以 structured output／function calling 約束模型時，
不可依賴 JSON Schema 的組合語意；分支必須自我完備。

## 5. 發現：拼字軸與內容軸必須結構性分離（Log 96–98）

**問題**：原文有錯字時，正確的引文**不可能存在**。模型寫 `regulator`、
使用者打成 `regualtor`，比對失敗，整份（正確的）解讀被丟棄。

**為何相似度門檻不可行**：`network → regulatory network` 的相似度**不低於**
`regualtor → regulator`。單一門檻鬆到能救錯字，就同時放行「多一個原文沒有的限定詞」，
而那個限定詞正是決定選哪個工具的東西。

**做法**：引文對齊到原文中**同長度的連續詞段**，逐詞配對，加三條收緊約束：

1. 容許的編輯距離隨詞長縮緊（≤4 必須全等；5–7 ≤1；≥8 ≤2），用 Damerau（含換位）。
2. **兩個都是領域詞時必須全等**。`mirna` 與 `mrna` 只差一個編輯而指不同分子。
3. 非 ASCII 詞不做容錯（`分組`／`分類` 也只差一個編輯）。

**單調性**：逐字比對先跑，對齊只在其失敗後才問，故**只會新增對齊、不會移除**。
以 27 題語料所有連續片語（500+ 個逐字命中）驗證。

**結果**：

| | 1a 前（r24） | r25 | r26 |
| --- | --- | --- | --- |
| `unmatched` 條目 | 60 | **0** | **0** |
| 走「未查證仍接受」路徑 | 3 | **0** | **0** |
| `misspelling` 類有被接受 outcome | 0/12 | 10/12 | 7/12 |
| 推薦錯工具／forbidden／unsafe | 0／0／0 | 0／0／0 | 0／0／0 |

**注意**：`unmatched` 60 → 0 是結構性的（程式直接後果，兩輪皆然）；
`misspelling` 那一列是分數型，且該指標同碼離散為 3，**不可單獨引用**。

## 6. 發現：matched-control 的顯著結果（Log 111／112）

**失敗類別**：第一次解讀把角色（regulator／target／entity）寫進 outcome，
卻沒有對應的證據條目。這在拼字問題修好之後是最大的損失來源——
兩輪 162 次試驗中，`missing_evidence` 有 **126/165（76%）** 屬角色維度。

**設計**：重建一個**唯一缺陷是角色證據**的第一次解讀（離線驗證過 issue 只有這一類），
四題皆以角色為判別維度。只變動程式碼，量第二次呼叫的修復正確率。

**基線的失敗機制**（36 次試驗，attempt 2 殘留）：

| | 次數 |
| --- | --- |
| `role_entity:regulatory_network` | **38** |
| `missing_evidence:entity_type=sample` | **26** |
| patch 動了 ≥9 個 outcome 欄位 | **14 / 24** |

被要求「補一條引用」的審查層**改寫了整個 outcome**，並塞入 `entity_types=["sample"]`
——那正是本研究唯一「推薦錯工具」的成因（Log 76）。

**介入（單一變數，結構性）**：當第一次解讀的 issue **全部**是 `missing_evidence` 時，
patch 不得改動 outcome 欄位，只套用其證據增刪。
語意依據：`missing_evidence` 說的是「這個值沒有引用」，不是「這個值錯了」；
值錯了有別的 issue 碼會講。**未使用 prompt 措辭**。

**三步結果**，每一步的門檻都在跑該步之前由凍結的基線算出並寫死：

| 程式狀態 | 逐輪 | 合計 | 對前一步 | 對原始 |
| --- | --- | --- | --- | --- |
| 原始 | 1, 1, 0 | **2 / 36** | — | — |
| ① citation-only 不改 outcome | 8, 7, 7 | **22 / 36** | p = 3.1×10⁻⁷ | p = 3.1×10⁻⁷ |
| ② 移除項指令正規化 | 8, 7, 10 | **25 / 36** | **p = 0.31（未達）** | — |
| ③ citation-only 忽略移除項 | 12, 11, 12 | **35 / 36** | p = 0.0015 | **p = 5.3×10⁻¹⁷** |

**① 的介入**：issue 全為 `missing_evidence` 時，patch 只套用證據增刪、不套用 outcome
覆寫。機制確認 `role_entity` **38 → 0**、`missing_evidence` **28 → 0**。

**② 未達顯著，且違反了「不得換位置」的事前判準**：patch 從此能解析，
於是 11 次失敗中只有 3 次真的修好，其餘 8 次把失敗從線路層搬到語意層
（attempt 2 出現基線沒有的 `missing_evidence` 36 次）。
**它被保留，但只以「不該為一個必然無效的移除指令丟掉整份格式正確的修復」的
正當性保留，不主張改善修復率。** 它真正的貢獻是讓失敗可診斷。

**③ 的成因來自 ② 換位置後的錯誤碼**：逐試驗比對顯示 **8/11** 的失敗是
patch 移除了 attempt 2 隨後抱怨缺少的那幾條證據
（`('operation','infer')` 與 `('artifact_type','regulatory_network')`，各 8 次）。
`evidence_only=True` 保持 outcome 不變，**因此沒有任何證據會變成過時的**，
該路徑下的移除只能撤回一個 outcome 仍主張的值。忽略之後：
重疊失敗 **8 → 0**、attempt 2 `missing_evidence` **36 → 0**。

**必須一併陳述的限度**：候選組的 patch **仍有 18/25 動了 ≥9 個欄位**。
**模型行為沒有改變**；改變的是「在只問引用時不接受它改值、也不接受它撤回」。
效果來自套用階段的限制，不是模型端的改善。

**唯一殘餘的 1/36 是正確的拒絕**：審查層為 `target_type=gene` 補了一條 explicit
證據，而該請求從未提到 gene。不應該去「修」它。

**此設計也能否證**：② 以 p = 0.31 未達自己的事前門檻。不是只會產出好消息。

## 7. 發現：路由正確 ≠ 數值正確（Log 85–89、103–108）

**設計**：以**上游／第三方自己的斷言原樣呼叫**，比對我方生產路徑的輸出。
容差一律取自方法作者，不自訂。

| Capability | 基準 | 斷言 |
| --- | --- | --- |
| SAMBAR | 上游 ground truth | 差 3.5×10⁻¹⁸ |
| COBRA | 上游 ground truth | `assert_frame_equal(rtol=1e-10)` |
| OTTER | 上游 class API | **抓到缺陷：安靜產出錯數字** |
| GIRAFFE | 上游 ground truth | **抓到缺陷：完全跑不起來** |
| CONDOR | 上游 ground truth | 全數通過 |
| LIONESS ×3 | 上游 class API | `np.allclose` |
| **PANDA** | **MATLAB 第三方** `panda_gt_matlab.csv` | `rtol=1e-12, atol=1e-12`；87×1000，實測差 **1.4×10⁻¹³** |
| **PUMA** | 上游 `matlablike_test_puma.txt` | `rtol=1e-5`（需生產路徑可選 `modeProcess`） |

**核心數字**：**最先核對的 5 個 capability 就抓到 2 個真實缺陷**，
而在那之前路由層測試全綠、證據契約全部成立。

**因此**：agent 系統只測「選對工具」會系統性高估。
兩個失敗面獨立，需分別量測。

**附帶抓到的上游缺陷**：`Puma` 未繼承 `Panda`，
`Panda.processData` 內經名稱改寫的 `self._Panda__remove_missing` 在 `Puma` 實例上不存在，
**`remove_missing` 在 PUMA 從未生效過**（PANDA 正常）。
恢復可達性後 PUMA 與 PANDA 在同一組先驗下都過濾到 **913** 個基因。

## 8. 發現：被記載的問題本身需要被量測（Log 91、100、102）

三個寫在交接文件裡的「已確認問題」，建立量測後實測為：

| 記載的問題 | 實測 |
| --- | --- |
| 「審查為消解引文失敗而把欄位降級成 `unknown`」 | **789 次試驗中 0 次** |
| 「模型不提供判別維度卻被記為完全正確」 | **34 次 `exact` 中 0 次**缺判別維度 |
| 「歧義匹配講不出真實候選」 | **69 次中 56 次已具名列出**；真正的缺陷是 **63/69 從未被評分** |

第一項的成因可以精確指出：一個比率量在語料 A，一個機制觀察在語料 B，
兩者被接在一起，而**沒有任何紀錄能連結它們**。建立該連結的儀器一落地就否證了它。

**可引用的結論**：agent 系統的「已知問題清單」會累積不存在的問題並排錯優先順序；
清單本身應被視為待驗證的假設。

## 9. 發現：閘門會在環境壞掉時保持綠燈（Log 109）

QA 環境掉了整組框架套件（`langchain_openai`／`langchain_core`／`langgraph`）。
相容層退到替身，**離線閘門仍回報 1501 passed**，
唯一症狀是 `skipped` 由 24 悄悄變成 34——而該數字無人在看。
（該上升當時被誤歸因於新增的 Docker 測試。）

**建議**：`skipped` 必須與 `passed` 一起報告；跳過數上升而沒有對應的新增跳過測試，
就是環境問題。

## 10. 不能主張的

- **任何輪次間的 pass rate 比較**。同碼替身即差 3。
- **任何逐題改善**。同碼替身即有 6/27 題不同。
- **`misspelling` 類接受率 0/12 → 3/12**（1c）。該指標同碼離散為 3，落在底線上，已撤回。
- **工具正確 20 → 22**。同碼離散為 1，已撤回其成效意味。
- **union 模式的 PUMA 數值正確性**。上游未提供該模式的參考檔。
- **「模型變得更會只改該改的欄位」**。第 6 節的效果來自套用階段限制，模型行為未變。
- **PUMA + `remove_missing` 的數值正確性**。無第三方參考；只證明兩條過濾路徑
  對「哪些基因該留下」的答案一致（同為 913）。
