## 做了什麼（程式 `054cca5`，修正 `f448ec8`、`f6fa41c`）

- **fact agent**（gpt-4o-mini）：目標明確時，每輪呼叫一次。它讀請求和候選 workflow 的合約原文，提出「使用者不確定、而且會改變判定」的事實。
- **R1–R6** 由程式驗證。R1 是兩個讀取者都要同意：fact agent 的引文必須和能力檢查讀到的不確定之處重疊（`UnknownAbout` 加上 `other`，記錄任何不確定的引文）。
- **R5**：每個 workflow 的 YAML 加入 `input_checks`，內容必須是合約自己的原文，由 policy loader 驗證。輸入檢查會查到的事實，只說明、不追問。
- 舊的 11 種 dimension 在 fact agent 有執行時改為 shadow（`FactCheck.legacy`）。fact agent 沒執行時（失敗、沒有預算、沒有候選），舊機制照常運作。
- ASK 回覆列出每個問題、兩種答案各導向什麼，以及使用者原話和合約原文。

## 還沒解決（需要使用者決定，沒有改）

1. **兩種答案導向的結果沒有驗證**。結果是模型寫的，R3 只檢查值是否合法。p2b 的例子：
   - C06 寫「If no: PUMA does it instead」，但 PUMA 也需要 TF。
   - C36 寫「If no: no registered workflow」，但 LIONESS-PANDA 做得到。

   提案：程式用能力檢查的 sheet 驗證每個分支（例如 other_workflow 必須是檢查認可的 workflow），對不上就刪掉那一行。這超出 spec 第 6 節的 R3，屬於設計變更，需要先記入 spec 變更紀錄並經使用者同意。
2. **能力檢查模型解碼失敗**。p2 有 9/56 次（p0 6、p1 5），ask 類有 4 題因此成為 UNCHECKED。這是 spec 第 11 節列的風險（nemotron 輸出截斷）。本階段量到：離線重讀 3/47、實測 9/56。對策屬於能力檢查本身，不在第 2 階段範圍內。
3. **不該做的誤承諾 3 題**（C17 lambda 必須成對、C18 用表現量直接跑 CONDOR、C57 COBRA 基因數少於樣本數）。第 0 階段的失敗型態 4 已列出，第 2 階段沒有涵蓋。依 spec 第 11 節，要處理需走變更流程。
4. C37 的 UNCHECKED 與 CLARIFY 先後順序：使用者已決定維持現狀。
