## 1. 研究方法（可放入論文的方法章節）

所有會改變行為的修改，都用同一套**事前登錄（pre-registration）協定**驗證。

1. **凍結：** 先把候選修改做成補丁並記下 sha256（例如 `dp_frozen.patch` = `02867cff064c`），寫入 `FREEZE*.md` 並 commit。
2. **隔離撰寫保留集：** 由一個**看不到 repository** 的 subagent，只依任務說明寫一組 32 題的新題目（7 個家族各 4 題，加上 4 個陷阱題）。
   - 同一家族的資料描述逐字相同，只換研究問題，形成最小對照。
   - 每題都有標註：使用者有沒有 prior／miRNA、這題需不需要、該不該追問、可接受的工具。
3. **事前宣告：** 在任何 live 呼叫之前，把判定門檻與「讀過標註後、只靠推理寫下的風險」寫進研究紀錄並 commit。
4. **live 比較：** 基準（現行程式）與候選在各自的乾淨 git worktree 執行。每臂 32 題 × 3 次，共 192 個 session，兩臂交錯，模型為 gpt-4o-mini。
5. **決定：** 判定全部成立才保留，任一不成立就 revert。事後不改判，也不在看過結果後改門檻。
6. **有效性規則：**
   - 遇到 provider 錯誤（連線、逾時）的 session，把原檔與 trace 移到 archive 後重跑一次。
   - 看過的保留集不再拿來做結論，只用於校準。這個 session 結束時已累計 23 組。

**協定的價值（論文可引用的實例）：**
- **分析器的自我測試抓到候選的真實缺陷：** Log 380 在看過的題目上試跑時發現，撤掉推薦會連帶清掉後續問題，使回覆掉到預算後備文字。這是在讀新保留集之前修好的，並記錄為 Amendment 1。
- **「回覆可重現」的判定抓到不確定性 bug：** Log 381 的 H2 發現引文取自 Python set，順序隨行程不同，同一個決策會引用不同句子。
- **分層判定區分「機制」與「輸入」：** Log 383 的呈現層全部滿分，失敗全在輸入讀取，因此能精確定位問題。
- **事前公開的風險多半準確：** Log 383 的 15 個失敗 session 中，12 個屬於事前寫下的風險。

## 2. Codex 的修正（`0026820`）

**問題：** 語意解讀出錯時的修補範圍太大（可能改寫整個目標），結果欄位由第一筆證據決定，claim 的來源不一致。

**改法：**
- 修補只能改出錯的那個假說與它自己的欄位；
- 同一欄位的證據全部收集後才決定一次；
- 已設定的值不被覆寫；
- 驗證錯誤分成五類，各有修補指示；
- 實驗性的 claims 契約（`semantic_contract="claims"`，非預設）從單一 claim 投影出結果與證據。

**為什麼有效：** 修補範圍縮小後，一次修補不會破壞其他已正確的部分。模型可見的 prompt／schema 指紋不變（legacy `e920bf3b5d57`、claims `743b2dd0d73a`）。

**量化：** 只以 HEAD 加這批檔案測試，3308 passed／35 skipped。

## 3. 第 1 項：分開「工具適合」與「使用者允許執行」（`2c6b1c6`）

**問題（診斷 F1、F2、F7）：**
- 「推薦工具，不要執行」會被當成執行意圖；
- 否定的搜尋（「不要搜尋」）被改成獲准搜尋；
- 「只解釋」被當成要檢查輸入。

工具匹配與授權混在同一個判斷裡。

**改法：**
- 新增程式持有的 `OperationAuthorization` 紀錄，與工具匹配分開。
- 只有「能授權的文字」可以把請求提升成操作。不能授權的文字包括：否定句、引號內文字、轉述他人的話、過去式描述、只解釋。
- 使用者的禁止成為**否決（veto）**：不論誰提出執行都會被拒絕，而且否決只能移除權限。
- 預覽旁的「不要執行」代表「現在不要」，不拒絕，以免擋到之後的 `/execute`。

**為什麼有效：**
- 否決在設計上只能減少執行，不會新增錯誤的執行，所以安全性不依賴召回率。
- 判斷是確定性的程式，可以完整重播驗證。

**量化：**
- 新增 46 個測試；
- 離線重播 982 個已記錄的真實請求，確定性判斷有 12 處改變，全是修正；
- 18 個實際會執行的決策中，現在拒絕 2 個，兩個都是正確的拒絕，例如「請先只做 preflight，不要執行 PANDA」原本被記錄成 `run_panda`；
- 模型可見內容不變。

## 4. 第 2 項：跨階段共用的需求紀錄（`d9f003b`）

**問題（診斷 F3，以及兩個新發現）：** 不同階段讀不同的文字。

1. **長訊息：** router 只看最後 6,000 字。一則 7,379 字、開頭是「Run PANDA with …」的訊息，router 看不到要跑 PANDA，planner 卻看得到。
2. **接受建議後：** 使用者在目標中寫的輸出路徑被換成預設路徑。
3. **接受建議後：** 使用者指定的輸入檔被遺忘，反而問要選哪一組。
4. **只修 planner 會更糟：** evaluator 會把帶過來的值判為「不在請求中」，進而拒絕計畫。
5. **`/execute`：** 前一回合的值會遺失。

**改法：**
- 每一回合從完整訊息讀一次 `RequestRequirements`，記錄每個陳述值的來源（本回合或前一回合）、禁止條款與路由讀到的目標。之後所有階段都讀這同一份。
- router 讀「開頭 2,000 字＋結尾」的 routing window，並明示省略了多少。

**為什麼有效：** 單一事實來源（single source of truth）。各階段不再各自重新解析文字，所以不會一個階段看得到、另一個看不到。

**量化：**
- 上述 5 種遺失都重現並修正；
- 992 個已記錄請求沒有一個超過 6,000 字，所以 routing window 不改變任何既有輸入；
- 33 個已記錄的 ready 計畫，新的 evaluator 檢查沒有誤判任何一個。

## 5. 第 3 項：先讀研究目的再選工具（Logs 378–379，撤回）

**問題：** Log 378 的基準觀察發現，研究目的被正確讀出 27/27 次，但進入工具選擇 0/27 次。系統的順序是先選工具，研究目的只出現在回覆裡。

**改法（候選 `80c837a`）：**
- 研究目的改在 routing 之前讀取；
- 在一組同樣適合的工具中，由事先宣告的「證據強度格子」選出一個；
- 只有在所需輸入已說出時才選。

**結果（heldout19）：**
- 精確度與安全判定全部成立：選擇 7/7 可接受，對照題、因果題、預測題上 0 次選擇，回覆可重現。
- 但預先宣告的增益門檻是「研究目的分得開的家族數 +2」，結果只有 +1，所以撤回（`445df9d`）。

**為什麼沒過：**
- 門檻用家族為單位，而多數家族在現行系統就已因 exact match 分開（飽和）。
- 另一個家族被第 4 項的錯誤遮住：沒提 prior 卻直接推薦 GIRAFFE。
- 實際的增益是 D2、F2 從「沒有推薦」變成 COBRA 3/3。

**對論文的意義：** 指標的設計要避免飽和（改以題為單位），而且這一輪直接引出了第 4 項。

## 6. 第 4 項：方法適用性（Logs 380–381，兩次撤回，之後併入第 5 項）

**問題：**
- 工具會因為「輸入格式相容」就被當成答案，即使使用者根本沒有它需要的資料。
- 使用者有沒有 prior，原本靠字詞表判斷，兩頭都錯：
  - 「no transcription factor motifs」被當成有；
  - 白話描述的 prior（「maps of where transcription factors bind」）讀不到；
  - 「we only have RNA-seq counts」也讀不到。

**改法：**
1. **資料讀取由模型做、程式驗證：** 一個小的 data-facts 呼叫讀出 prior 與 miRNA 是「說出／排除／沒提」，並附原文引文。引文必須能在使用者的話中找到，否則降為「沒提」。
2. **擁有權規則（Log 381，程式規則，不改 prompt）：** 讀成「有」時，引文還必須落在使用者自己、現在的陳述裡，使用第 1 項的「能授權文字」。轉述（「my advisor says…」）、引號、過去（「last year … another cohort」）都不算。
3. **每個工具的適用性：** 依讀取結果判為能用、不能用（需要被排除的資料）、資訊不足（需要沒提的資料）。
   - 不能用的工具不再寫成「Selected path」，改成條件開頭，例如「GIRAFFE fits … but it needs a motif prior and a PPI network, which you said you do not have」。
   - 需要被排除資料的平手推薦會被撤掉。
   - fallback 推薦也加上條件。

**為什麼「精確」這一半有效：**
- 模型負責理解語意，程式負責判斷與驗證引文，避開了字詞表的兩種錯誤。
- 校準結果（看過的資料）：

  | 讀取方式 | 讀成「有」的召回 | 讀成「排除」的召回 | 把沒有讀成有 |
  |---|---|---|---|
  | 模型讀取＋引文驗證（第 20 組） | 30/30 | 36/36 | 0 |
  | 擁有權規則（第 16–19 組既有讀取） | 不變 | — | 0 次誤降（共 384 筆） |
  | 擁有權規則（第 20 組 T1、T2） | — | — | 6/6 正確降級 |

**為什麼沒過（召回那一半）：**
- **Log 380：** 指導教授說的「we need a motif prior」被讀成使用者有；另一種回覆格式不會追問；「預測題」也被追問。另外，M1 判定本身定義錯誤。
- **Log 381：** 「合作者還沒分享」被讀成排除；「資料庫涵蓋番茄」被讀成有；兩問合一時段落不出現；4/24 個 session 的 routing 沒有讀法。

**一個有價值的負面結果（論文可引用）：** 為了處理「只提到、不是自己的資料」，曾試著在 schema 加一個 `mentioned_only` 狀態。它修好了一個陷阱題，但讓「排除」的讀取召回大跌：

| 保留集 | 排除召回：原 prompt | 排除召回：加 `mentioned_only` 後 |
|---|---|---|
| 第 18 組 | 27/27 | 13/27 |
| 第 20 組 | 36/36 | 6/36 |

這證明在 prompt 裡改語意分類會牽動其他讀取，因此改用程式規則。這與之前 Logs 345–353 的結論一致：字詞表不泛化，prompt 措辭修正也脆弱。

## 7. 離線失敗歸類（Log 382）

**做法：**
- 對三輪現行系統的 288 個 session，以及兩輪第 4 項候選的 192 個 session，判定使用者看得到的失敗。
- 失敗類型：該問沒問、不該問卻問、跑不了的工具當答案、不適合的工具、回覆退化。
- 分類器在各自的程式碼下逐步重跑觸發條件，找出第一個擋下的位置。抽樣人工核對 13 例，歸因都正確。

**結果：** 現行系統 **76/288 個 session（26%）有失敗，共 89 個。**

| 共同原因 | 現行系統 | 第 4 項候選的殘餘 |
|---|---|---|
| A. 「要問什麼、要給哪個工具」散在各回覆模組的局部條件裡，例如只處理網路類結果、回覆類型白名單、需要替代工具、混合工具清單、三條推薦路徑各自決定 | 46（52%） | 14 |
| B. 「使用者有什麼資料」靠字詞判讀 | 27（30%） | 13（只剩邊界說法） |
| C. 「題目需要什麼資料」從 routing 列出的工具反推 | 16（18%） | 7 |

**對論文的意義：**
- 這解釋了 Logs 380–381「每修一條路徑，新題目就從另一條出錯」的現象：問題在共通機制，不在個別路徑。
- 由此設計出第 5 項。

## 8. 第 5 項：每輪一份資料需求計畫（Log 383 撤回 → Log 384 保留上線）

**問題：** Log 382 的 A 類與 C 類。

**改法（`interpretation/data_plan.py`、`TaskDecision.data_plan`）：**
1. **題目需要什麼，從問題本身讀：**
   - 讀取順序：研究目的引用的問題 → 使用者自己的問句（去掉引號內文字）→ 最後才用 routing 的讀法；
   - 不讀描述資料的句子，也不由 routing 列出的工具反推；
   - 只問預測或因果時，判為「不需要資料」，因為沒有任何已註冊工具能回答。
2. **使用者有什麼：** 依序看綁定的檔案、第 4 項的模型讀取，最後才看字詞。
3. **每種資料一個動作：** 說出 → 不動作；排除 → 說出並附該種資料自己的引文；沒提 → 追問。prior 已排除時，不追問 miRNA。
4. **所有回覆都呈現同一份計畫：** 原本的段落只問計畫要問的；回覆的最後一步會補上缺少的追問或聲明，對每種指引類回覆、逐讀法回覆、routing 失敗回覆都一樣。
5. **修正 Log 381 發現的引文順序 bug。**

**為什麼有效：** 決定點只有一個（計畫），呈現由最後一道檢查保證。新的回覆路徑不會再漏掉追問；這正是 A 類原因的解法。

**量化：**
- **Log 383（第 22 組）：**
  - 呈現層完全成立：計畫要問的回覆都有問 12/12，要說的都有說 12/12，沒有問到計畫以外的東西。
  - 「該問時有問」只有 3/15，與現行系統相同，未達宣告的 70%，因此撤回。
  - 失敗全在計畫的輸入：研究目的漏讀、陳述句目的、審稿人的轉述被讀成有、「打算下載」被 routing 當成下載請求、單引號內第三人的話被讀成使用者的問題。
- **Log 384（第 23 組，程式完全相同，重新宣告）：**
  - 主張縮小為它能控制的部分，加上「追問不少於現行系統」的不退步條件。這個範圍縮小是在新保留集寫成之前宣告的，Log 383 的撤回維持原判。
  - **14 項判定全部成立，保留上線：**

    | 判定 | 現行系統 | 計畫 |
    |---|---|---|
    | 已說明仍追問 prior | 11 | 0 |
    | 不需要的資料問題 | 14 | 3（都在單引號陷阱 T1） |
    | 跑不了的工具當答案 | 4 | 0 |
    | 說出排除 | — | 9/11 |
    | 呈現計畫的追問 | — | 19/19 |
    | 呈現計畫的排除 | — | 14/14 |
    | 問到計畫以外 | — | 0 |
    | 該問 prior 時有問 | 7/18 | 7/18（不退步） |
    | 該問 miRNA 時有問 | 0/6 | 6/6 |

  - 其他檢查：模型撰寫的回覆 0、回覆可重現（差異 0）、只多一個呼叫角色 `data_facts`、兩臂 96/96、全套件 3405 passed／35 skipped。

## 9. 為什麼保留下來的改動會成功（共通原則）

1. **模型負責讀，程式負責決定，並驗證引文。** 模型理解語意（「我們只有 counts」等於沒有 prior），程式檢查引文確實出自使用者，並做所有決定。這同時避開了字詞表的僵硬與模型自由發揮的不可控。
2. **把「適合」與「允許」、「需要」與「擁有」拆成獨立的紀錄。** 第 1 項的授權、第 4 項的擁有、第 5 項的需求，每一份紀錄只回答一個問題，彼此可以分開驗證。
3. **單一決定點與單一事實來源。** 第 2 項的需求紀錄、第 5 項的計畫，都讓所有階段或回覆讀同一份資料，消除「這裡看得到、那裡看不到」的整類錯誤。
4. **安全方向的設計。** 否決只能減少執行；計畫的檢查只會補上缺漏，不會改寫原回覆；被判為不能用的工具不會被刪除，只會加上條件。即使判斷錯誤，最壞的情況也是多問一次或少一個推薦，不會造成錯誤的執行。
5. **改契約的形狀（程式規則），不改 prompt 措辭。** 第 6 節的 `mentioned_only` 負面結果，就是這條原則的直接證據。

## 10. 為什麼撤回的改動沒過（也是論文的討論材料）

- **端到端的召回會被上游封頂。** 「該問時有問」要同時依賴三個讀取：研究目的、擁有、routing 授權。任何一個在新的邊界說法上漏讀，回覆層再好也救不回來。Log 383 的分層判定清楚顯示：呈現層 100%，失敗全在輸入。
- **每組新題目都有新的邊界說法：** 別人說的話、還沒分享、資料庫涵蓋、審稿人堅持、打算下載、兩問合一、陳述句。用規則逐一修補，就是已被證明不泛化的字詞表路線。
- **指標設計本身也可能出錯：** 家族層級的指標會飽和（Log 379）；M1 把系統原本就有的分辨問題也算進去了（Log 380）。之後改成以題為單位、分層的判定。

## 11. 限制

- 所有 live 評估都使用 gpt-4o-mini，每輪 32 題 × 3 次。同樣的程式在不同輪之間本身就有變動，這些輪次也不是彼此獨立的樣本。
- 保留集由隔離的 Claude subagent 撰寫並標註，沒有人工標註，可能帶有單一標註者的偏誤。
- 評估範圍是「資料適用性與工具選擇」，沒有涵蓋解釋品質等其他面向。
- 回覆卡片（UI）的「Inputs」選項跟隨段落；計畫最後一步補上的問題目前只出現在回覆文字裡。初學者用的群組網路說明，仍會自行追問 prior。
- 「該問時有問」仍受三個輸入讀取限制。
