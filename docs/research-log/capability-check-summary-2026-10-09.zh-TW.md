# 能力檢查層（防止「瞎掰 workflow」）整理：Logs 385–393（2026-10-08 ～ 10-09）

## 1. 問題與起點

使用者在 2026-10-08 提出：問一個沒有任何套件做得到的問題，系統卻給出一條 workflow，這比漏答更嚴重。

**基準量測（Log 385）**：自寫 24 題陷阱題，分 4 類：完全做不到（U）、近似誤解（N）、一半做得到（P）、對照（C）。每題跑 3 次。

| 類別 | 結果 |
|---|---|
| U+N（45 次） | 誠實 9 次（9 次全部來自「因果」模板）；瞎掰 14 次、含糊 11 次 |
| C（18 次） | 全部正確 |

**根因：routing 的投影。** routing 輸出的 `RequestedOutcome` 只能從固定詞彙挑一個 artifact，沒有「以上皆非」可選。因此擬時序、剪接、空間反摺積都被塞進最接近的 `regulatory_network`，matcher 再依 registry 列出候選。模板文字本身沒有亂講功能。

**關鍵觀察：模型讀得懂目標，但歸類錯。**
- 45 次中有 42 次，模型引用的原文正是使用者要的結果。
- 但只有「因果」「預測」這兩種詞彙裡已有的類別歸對，其他都被塞到最近的類別。

## 3. 最終設計（怎麼改的）

處理流程：

```
使用者請求
 ├─ routing（原有，gpt-4o-mini）→ 候選 workflow
 └─ 能力檢查（新增，nemotron，routing 後立刻呼叫）
      1. code 先把請求切成句子；schema 每一句一個必填欄位（s1..sn）
      2. 模型對每句給出 role（background / asks / methods_question / mixed），
         再分三籃：has（資料）、about_methods（方法問題）、asks（要求）
      3. 只有 asks 能點名能力表條目（ID 是 enum，無法捏造）；
         每個 ask 另外帶型別欄位：scale、omics_layers、data_unit、regulator_kinds、needs_sign
      4. code 驗證：引文要在原文中（容許近乎逐字）→ 依型別欄位排除不相容的條目 → 判定每項要求的狀態
      5. 覆蓋檢查：某句沒有任何引文覆蓋，又不是 background／methods 句，就列為「未檢查」
      6. 每個結果都做不到、而且每句都讀過 → 完全缺口
      7. 若完全缺口會清掉 routing 已 exact 配對的 workflow → 以 workflow 為單位再問一次是／否（第二意見）
 └─ 回覆
      - 完全缺口：列出「我理解你要」，說明照你問的方式做不到，保留已驗證的替代說明，不提供 workflow
      - 其他情況：在原回覆開頭加上「我理解你要」，每項標示：可用／需外部步驟／部分／做不到
```

**能力表**（`scripts/capability_sheet.yaml`，共 31 條 produces、32 條 near-miss、2 條全 registry 不支援）：

- **封閉世界**：只有 produces 條目能證明「做得到」，near-miss 永遠不參與判定，只用來解釋。所以 near-miss 列不完整也不會出錯。
- **每條都有出處**：論文，或 [EXEC]（執行器實際寫出檔案的那行程式碼），或 [REG]（已驗證過的 registry 句子）。
- **型別欄位**：`granularity`、`layers`、`regulators`、`signed`、`data_units`。
- **fail-closed**：缺 source、ID 重複、某個 run action 沒有 produces 條目等情況，都會讓 import 直接失敗。

**設定**：`.env` 中的 `OPENROUTER_CAPABILITY_MODEL=nvidia/nemotron-3-super-120b-a12b:free`，輸出上限 6000 tokens。

## 4. 為什麼這樣做能成功

1. **補上「以上皆非」。** routing 失敗的根因是「必須從詞彙裡挑一個」。新的契約讓「沒有任何條目交付」成為正常答案，判定交給 code，採封閉世界。
2. **把模型做不好的判斷搬給 code。**
   - 條目 ID 用 enum，模型無法捏造。
   - 引文由 code 驗證。
   - 每句一個必填欄位：v1 用可變長度的清單時，3/4 的情況模型只回第一句。
   - 只有 ask 能點名條目：曾經出現一句資料描述被附上 16 個 near-miss。
   - 型別欄位由 code 比對：mini 曾把「每個細胞一張網路」給 LIONESS、「lncRNA 當調控者」給 PUMA、「正負號」給 PANDA。這些都是模型層級的判斷錯誤，改成比對型別後就不再依賴模型。
3. **不對稱的權限。** 檢查只能降級，也就是清掉候選，不能新增 workflow；呼叫失敗或被預算擋下時，就照原本的行為回覆。安全的方向永遠是預設。
4. **兩個獨立讀者，只在衝突時再判一次。**
   - 三輪的假缺口（HC7、JC6、KC8）全部是同一型：routing exact，檢查卻交白卷。
   - 第二意見只在這種衝突時觸發，而且以 workflow 為單位問「這些結果合起來是否交付」。逐條目問會讓「網路＋顯著性」這種跨條目的需求被誤判為「否」。
   - heldout4 中觸發 8 次：救回 2 次正確的對照，維持 5 次正確的缺口，錯放 1 次。
5. **模型能力是瓶頸，而且錯誤是系統性的。**
   - mini 的錯誤在同一題 3 次重複中都一樣，所以多跑幾次取多數無效。
   - 只有換模型才能解決：重放實驗中，對照題假缺口 mini 4–6/60，nemotron 與 gpt-4o 都是 0/60。
6. **嚴格的量測紀律避免自我欺騙。**
   - 每輪都在執行前凍結判定，並使用全新的保留集。
   - 兩臂交錯執行，標註由獨立子代理盲標，任何一項判定不成立就撤回。
   - 前三輪都被撤回：若沒有 G2（對照題假缺口必須 = 0），第一輪「33→4」看起來就已經成功，但其實會讓 GIRAFFE 的核心功能被說成做不到。

## 6. 可以放進論文的內容

### 6.1 問題定義
- **能力幻覺（capability hallucination / false affordance）**：工具導向的 agent 會把「沒有工具做得到的需求」投影成最接近的可支援類別，並給出 workflow。
- **量化證據**：基準 45 次中只有 9 次誠實。
- **機制證據**：42/45 引文正確，但類別錯誤。「讀懂」與「歸類」之間的落差，是一個可以寫的發現。

### 6.2 方法貢獻
1. **以執行器為根據的封閉世界能力表**：每條都有出處，near-miss 不參與判定。
2. **逐句結構化讀取**：每句一個必填欄位、只有 ask 能引用條目、引文由 code 驗證、覆蓋檢查。
3. **型別相容性檢查**：資料單位、調控者種類、正負號、層數、粒度，由 code 比對。
4. **不對稱權限**：只能否決，失敗時退回原本行為。
5. **衝突觸發的第二意見**：兩個獨立讀者不一致時才再判一次，以 workflow 為單位提問。

### 6.3 評估設計（方法學也可以是貢獻）
- 陷阱集分 U、N、P、C 四類，各有標註的 `core`、`nearest`、`accept`。
- 每輪事前凍結判定；保留集每輪重新撰寫。
- 兩臂交錯執行，盲標，判定不成立就撤回。
- 用「只重放檢查呼叫」來比較模型，成本遠低於跑完整 session。

### 6.5 可討論的發現
1. **結構勝過措辭。** 每一次改善都來自 schema 形狀或 code 檢查，例如每句一個欄位、只有 ask 能引用、型別欄位；沒有一次來自改 prompt 用詞。這和專案先前「禁止用 prompt 措辭修正」的結論一致。
2. **系統性錯誤無法靠多數決消除，必須換模型或換結構。**
3. **免費的開源模型在這個窄任務上可以接近 gpt-4o。** 對照題假缺口兩者都是 0/60，成本為 0，代價是延遲。
4. **「誤說做不到」需要獨立的判定門檻。** 只看瞎掰率會誤判成功：第一輪 33→4 時，GIRAFFE 的核心功能被說成做不到。
5. **建立能力表本身就是一種稽核。** 它揭露了模板宣稱、但執行器並未產出的功能，以及上游套件的錯誤（Log 386）。
6. **評估方法的保守性。** 依事前宣告撤回了三次候選，避免把開發集上的成功誤當成泛化能力。

### 6.6 效度威脅（論文必寫）
- 標註者是 LLM。
- 題目由研究者撰寫，只有英文。
- 每組 35 題、重複 3 次，重複之間不獨立。
- 保留集在使用後即成為已看過的資料。
- 免費模型的服務穩定性不受我們控制。
- 基準與候選共用同一套 routing。
