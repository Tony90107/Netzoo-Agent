## 誤拒絕（3 項）

MX03、MX09、MX10 是同一種問題：可做與不可做的需求被併成同一個引文，或不可做的條件被套到整個請求，於是可做的部分（兩層 DRAGON、TF＋miRNA 的 PUMA、單純 CONDOR）也一起被拒絕。

## 新發現的缺陷

- **S138（P30）**：「Outputs can go to /registry/sambar_run1」被歸成交付類，列為不可做的需求。這是 4–5 項拆出交付類後的誤判；標準答案的需求不受影響，但回覆前後矛盾。
- **計畫綁定了錯誤的檔案或 toy 資料**：run 回合的輸入精靈沒有綁定使用者寫出的檔名（例如 P21 的 `yeast_stress_logc.tsv`），改為列出 toy 資料組。
- **輸入需求誤判**：多題使用者已說有 motif／PPI，回覆仍問「Do you have a motif prior and a PPI network?」（S001、S046、S116 等）。

## 偏離凍結內容之處

1. **`a24` 作廢**：7696e69 混入另一個 session 尚未提交的修改，CLI 無法啟動；修正為 3529927 後以 `a24b` 重跑。題組與標準答案都沒有改動。
2. **run 回合沒有重播**：`replay_sessions.py` 只重播詢問回合，24 個 run 回合使用錄製的回覆。126 個詢問回合的重播都與錄製一致。
3. **run 回合的標註規則**：packet 只收錄輸入精靈的文字，缺少 CLI 先顯示的「✓ Workflow — X」。因此我複核了全部 24 個 run 回合，不只凍結指定的抽查範圍：
   - 可做需求改為 GIVEN_IF_INPUT。
   - 屬於該 run 本身對象或限制的不可做需求，改為 GIVEN_IF_INPUT（誤承諾）。
   - 未被提到的不可做附帶需求，維持 OMITTED，在 run 層另報。

   不套用這條規則時，FAR 為 9/62 = 14.5%，等級仍是 D。
4. **U09** 依裁定不計分；**U03** 照標準答案算未追問（見上）。

## 可行的下一步（依影響排序）

1. **方法設定層的能力**：把各 workflow 可調整的控制項與硬上限（最少樣本數、資料量上限、不支援的參數或變體）寫進能力表，並納入判定。這可以處理 7/11 的誤承諾。
2. **同一引文中的多個需求**：條件只套用到它所限制的那一項，不要一次清空整個請求。這可以處理 3/3 的誤拒絕。
3. **run 路徑套用多輪條件**：K02 這類多輪條件要在 run 路徑上生效。
4. **追問**：擴充未知類別（變異來源、資料型態、樣本數），並處理同一題兩次執行不一致的問題。
5. **修正交付誤判**：「輸出資料夾」不應被歸為交付。
