# Harness repair P3：任務事實跨回合保存與兩輪追問（2026-10-23，開工前宣告）

依 spec 第 7、8 節與計畫 P3 撰寫。本檔在寫任何 P3 程式之前宣告；要改內容，須先由使用者決定並記在這裡。

## 現況（探索結果，皆在 `61ccc3b7`）

- **ASK／CLARIFY 回合不被當成待續。** 這類回合存成 `respond_only`：一次性（one-shot）且沒有 `--keep-session` 時，回合結束後 session 會被刪掉；`--resume latest` 找不到它，清理時也可能被刪。
- **使用者的回覆不會對應回問過的題。** 下一回合只把「Previous NetZoo goal: … User follow-up: …」的整段文字交給讀題重讀。目標文字會巢狀疊加，而且只保留最後 4,000 字。
- **沒有跨回合的追問輪數，也沒有「已經問過」的判斷。**
- **對話壓縮**最多保留 12 則訊息、16,000 字元，較舊的整則丟掉。存檔裡的 `version` 從來沒有被讀取。
- **CLI、互動聊天與 daemon 都走 `ConversationMachine.run_turn`。**

## P3 做什麼（最小版本）

1. **`TaskState`**（`contracts/task_state.py`，有版本號）記錄：
   - `task_id`、`revision`；
   - 開啟這個任務的原始請求（去掉巢狀前綴）；
   - 待答問題：每題有穩定的 `question_id`，並附上可對應的選項；
   - 已答事實：答案值、使用者原文、是否已被更正取代；
   - 科學追問的輪數，以及狀態（active、exhausted 或 closed）。

   它存在 session 檔的獨立欄位，不在訊息裡，所以不受壓縮影響。
2. **回合結束時更新**（`engine/task_updates.py`）：
   - 判定為 ASK 或 CLARIFY：輪數加 1，待答清單改成本回合問的題加上排隊的題。
   - 判定為其他：任務關閉，已答事實保留作歷史。
3. **回答對應只用程式**，下面兩種以外一律不對應，問題維持待答：
   - 有固定選項的題（維度值與其標籤、count 的候選值、選項題的原文）：回覆中恰好出現其中一個選項時才對應。
   - agent 的 yes/no 題：只有在待答清單裡只有這一題時，才把開頭的 yes/no 對應過去；有兩題時，一個「yes」不對應任何一題。
4. **已答的維度與 count 不再問。** 答案值用註冊的 outcome 套到該列：
   - 有對應結果：該列可做。
   - 沒有對應結果：該列不可做，理由寫明使用者的答案和程式核對的對應關係。

   agent 題只記錄，不據以下判斷，因為它的 yes/no 方向不可靠（ask_facts 的 open item 1）。這類題目重問時，靠輪數上限收斂。
5. **兩輪上限。** 同一任務已追問兩輪後，再要 ASK 或 CLARIFY 時：
   - 判定種類不變，標記 `clarification: exhausted`；
   - 回覆說明已問過兩次、不再追問，列出仍缺的資訊；
   - 不判為做不到，也不執行；
   - 使用者之後主動補充，仍會更新判斷；從存檔續接時輪數不歸零。
6. **更正與換任務：**
   - 回覆對已答的題給出不同選項時，舊答案標為被取代，換上新答案，並清除舊的預覽與待執行計畫。
   - 回覆意圖為 `new_goal` 時開新任務，舊事實不帶過去。
7. **待續與續接：**
   - 有待答問題的任務算待續：不被一次性刪除，`--resume latest` 找得到，清理時保留。
   - 從存檔續接時一併讀回 TaskState。
8. **版本：**
   - 舊 session 沒有 TaskState：照舊開始，不從回覆文字生出事實。
   - TaskState 版本比程式新，或內容損毀：拒絕續接並說明原因，原檔保留。
   - TaskState 從不保存任何執行核准。

**不做**（留待之後）：

- 自由文字的回答由模型解析成 FactPatch；
- 以 TaskState 改寫交給讀題的文字（會改變模型讀取，屬於 live 才能量的改動）；
- 資料集或 subject 層級的版本相依；
- daemon 專屬的 UI。

2. 單輪 replay（B2，P2b → P3）**0 個判定改變**：錄製的讀取沒有 TaskState，判定必須和 P2b 相同。

   - A12：更正答案、換任務。
   - A13：兩輪仍未解、從存檔續接、多次重開。
