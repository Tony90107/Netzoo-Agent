## 第 1 輪後的離線修正 (1)–(3)（2026-10-24 使用者核准；寫程式前宣告）

追查錄製後，三個問題的原因如下。

- **(1) 當機（M11）**：`--resume` 的佇列訊息遇到等待中的 plan 時，`next_action` 不管 action 是什麼，一律呼叫 `_recheck`。M11 的等待 plan 是 legacy handoff 路徑留下的 `no_tool` / `needs_input`，`WorkflowContinuation` 只接受 run action，所以出錯。互動路徑（`_submit_clarification`）本來就有「只有 run action 才重新檢查」的判斷，只有 resume 路徑漏了。
- **(2) 更正沒有重新判定（M01 D/E）**：第 2 輪留下等待輸入的 run，run 進入暫停，第 3 輪續接時沿用第 2 輪的 token 用量（42,638 / 60,000）。重新檢查需要的 capability check 被預算擋下（`budget.blocked`），run check 只能回 unconfirmed，結果判為 UNCHECKED/held。不是判定規則錯，而是預算被前一回合用掉了。
- **(3) S04 的錯誤理由**：「GIRAFFE does not give it: …」來自 `stated_reasons.stated()` 對 near-miss 的處理：非 registry-wide 的 not_by 一律保留。near-miss 條目沒有任何可核實的 claim（32 條都沒有），「使用者問的就是這個 near-miss 結果」這個前提完全是模型讀取的判斷。
  - **更正第 1 輪紀錄**：這不是 P2 第二層新加的。A 也有同一個分支，只是 A 在 S04 的讀取沒有給 not_by。若有，A 會說「no registered workflow produces this. GIRAFFE does not give it…」，更糟。P2 改的只有前半句。

**修法：**

1. `engine/machine.py::_recheck`：action 不是 run 時，不重新檢查，訊息照 M2 之前的做法當作新回合（`_accept_task`）。佇列路徑因此與互動路徑一致。
2. 同一個 `_recheck`：重新檢查的回合清掉沿用的 `active_usage`，用自己的回合預算。理由：請求已經改了；這和 Log 404 對封存 run 的處理（「新的回合預算」）一致。輸入精靈的回答（路徑、編號）不經過 `_recheck`，照舊沿用預算。
3. `interpretation/stated_reasons.py::stated()`：只保留 claim 已核實的 registry-wide 理由；單一 workflow 的 near-miss 不說，那一列改用第二層（引用原文、說明對不到、列出它自己點名的 workflow 提供什麼）。只影響回覆文字，不影響判定。

**門檻：**

  - (1) resume 後遇到非 run 的等待 plan、使用者提出新請求，不當機；
  - (2) 等待中的 run 收到更正時，這一回合不帶舊的 token 用量，且仍走 recheck；
  - (3) near-miss 不被說出、registry-wide 照舊。
- **完整 `tests/` 通過**。舊測試若寫死 near-miss 句子，依本決定更新並列出。
- **B2 replay：判定 0 改變**（三項都不改判定層；replay 也會讀到 p5 的新錄製）。
- **理由稽核**（`layers.py`）：列出因 (3) 而改變的回覆數，以及被拿掉的 near-miss 行先前在 ROUND-19 judge 的判定（說對／說錯各幾則），作為代價。
