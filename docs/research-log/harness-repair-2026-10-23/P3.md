# Harness repair P3：任務事實跨回合保存與兩輪追問（2026-10-23）

依 [ROUND-P3.md](ROUND-P3.md) 的設計與門檻實作，內容沒有改動。只改程式，沒有呼叫模型，費用 **$0**。

## 改了什麼

### 新增的三個模組

| 檔案 | 作用 |
|---|---|
| `contracts/task_state.py` | `TaskState`（第 1 版）：`task_id`、`revision`、開啟任務的原始請求、待答問題（`PendingQuestion`，有穩定的 `question_id` 與可對應的選項）、已答事實（`TaskFact`，含答案值、使用者原文、是否被更正取代）、追問輪數，以及狀態（active、exhausted 或 closed）。`load_task_state` 遇到沒有版本、版本比程式新或內容損毀時丟出 `TaskStateError`，不會當成「沒有狀態」。 |
| `engine/task_updates.py` | 回合結束時更新任務（`after_turn`）；把回覆對應到待答問題（`bind_answers`），只用程式；續接時的回覆處理（`reply_answers`）：新任務關閉舊任務，更正答案則清除預覽與待執行計畫。 |
| `interpretation/task_answers.py` | 圖內兩件事：已答的維度或 count 待問，以使用者的答案套用註冊的 outcome 解除（`answered_check`）；同一任務已追問兩輪後，ASK 或 CLARIFY 標記為 exhausted（`clarification_rounds`），回覆開頭加一段說明。 |

### 接線

- `graph/router_invocation.py`：fact agent 之後、`needed_facts` 之前呼叫 `answered_check`。
- `graph/routing_planning.py`：`with_core` 之前呼叫 `clarification_rounds`。
- `interpretation/core_views.py`：exhausted 的 ASK 或 CLARIFY，回覆前面加上 `EXHAUSTED_NOTE`，判定種類不變。
- `session.py`：`save_session` 多存 `task_state` 欄位；新的 `waiting_session` 讓有待答問題的任務算待續，所以 `--resume latest` 找得到，清理時也保留。
- `server/history.py`：可續接的狀態多一個 `awaiting_answer`。
- `cli/bootstrap.py`：讀檔抽成 `resumed_session`，一併讀回 `TaskState`；版本或內容有問題時拒絕續接並說明原因，原檔不動。
- `engine/machine.py`：
  - 續接時帶入 `TaskState`；
  - 每個回覆先做程式對應；
  - 回覆被判為太模糊（needs_detail）但已經對應到答案時，照樣當成回答（例如只有一題時回「yes」）；
  - 回合結束時更新並存檔；
  - 有待答問題的一次性 session 不刪除。

### 回答怎麼對應

- 有固定選項的題（維度值或其標籤、count 的候選值），回覆中恰好出現一個選項時才對應。
  - 以整字或整個數字比對：「2,000」對應 2000，「0.200」不算提到 200，句尾的句點不影響比對。
  - 同一個字同時是兩題的選項時，兩題都不對應。
- agent 的 yes/no 題，只有在待答清單只剩這一題時，才把開頭的 yes 或 no 對應過去。
- 對已答的題給出另一個選項，就算更正：舊答案標為被取代、保留在紀錄裡，換上新答案。
- 其他回覆都不對應，問題維持待答。回覆原文照舊以「Previous NetZoo goal: … User follow-up: …」交給下一次讀題，所以主動補充的新條件仍由讀題處理。

### 已答的題怎麼用

- **維度與 count**：下一回合讀題若又產生同一個待問（同一維度、`unknown_quote` 和原本的使用者原文重疊，且答案值在 outcomes 裡），就直接用答案解除，不再問：
  - 答案對應到結果：該列可做；
  - 答案沒有對應結果：該列不可做，理由寫成「You answered "…" to "…": with …, none of the workflows matched to this result (…) gives it」，答案原文和程式核對的對應關係都寫出來。
- **agent 題**：只記錄，不據以下判斷，因為 yes/no 的方向不可靠（ask_facts 的 open item 1）。這類題目重問時，靠輪數上限收斂。

單元測試（`tests/test_clarification_budget.py`）涵蓋：

## 驗證時修掉的缺陷

新增的 A11 測試抓到：選項字後面接句點（「Somatic. Also …」）時不會對應。原因是比對邊界把句點當成小數點的一部分。改成只有句點後面緊接字元時（如 0.5）才算連在一起；開頭的「Yes.」、「No.」也一併修正。replay、理由與 fixtures 都不經過這段程式（錄製的讀取沒有 TaskState）。

## 仍然不支援的地方

- **自由文字的回答不由模型解析。** 「the first one」「the bigger panel」這類回答不會對應，問題維持待答；下一次讀題仍看得到回覆原文，判斷方式和 P2b 相同。
- **已答事實只在下一次讀題又產生同一個待問時才用得上。** 讀題若換了說法（不同維度，或原文不重疊），答案就套不上，可能重問一次，之後由兩輪上限收斂。
- **agent 題的答案只記錄。** 這類題目重問時，只靠兩輪上限收斂。
- **交給讀題的文字沒有改**（仍是巢狀的 follow-up 文字，只保留最後 4,000 字）。改用 TaskState 改寫讀題文字會影響模型讀取，必須 live 才量得到，所以這次不做。
- **`engine/machine.py` 剛好 1,000 行**，碰到模組大小測試的上限，之後要再加東西得先拆檔。
- **desktop 歷史清單會出現新的狀態 `awaiting_answer`。** `SessionsPane` 沒有它的標籤，會退回顯示「awaiting answer」；「Latest saved state」篩選選單也沒有這個選項，只在「All states」看得到。
- **多輪 live 沒有跑。** 多輪的效果（回答是否被對應、第三輪是否停問）只在程式層驗證過；要量 live，需另外提出題目、數量與費用。
