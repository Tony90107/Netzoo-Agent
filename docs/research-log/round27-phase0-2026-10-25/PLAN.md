  - 設定：漏 98、錯 31；

- **能力其實有寫在 registry 裡。** 例如 `sparsify` 在 `bonobo.yaml` 有定義，TF activity 在 `capability_sheet.yaml:255` 有一行。問題是 registry 用工程語言寫，使用者用研究目的的語言說。
- **2a（ROUND-26，`f7da8cbe`）已經試過「每個欄位自己的候選」：**
  - 召回大幅提高：選項單位修好 16、改壞 0；宣告單位修好 21、改壞 0。

  - **失敗的機制已經查清楚：** `setting_issue` 會把「credit 的 workflow 沒有的設定」直接變成限制，限制拿掉 credit，回覆再把它說成理由。例如 Q45 的「a separate partial-correlation network for each tumor」被連到 `DRAGON.output_format`，結果拒絕時說「LIONESS-DRAGON has no setting for …」。
  - 2a 的結論：**沒連到的設定會安全地用預設值，連錯的設定卻會拒絕並給錯的理由。所以設定欄位的精確率比召回率重要。**
- **結果連結（2b）從來沒做過。** h6 另有一個精確率問題：「沒有對應產出的用語」只對 3/12，誤記功 9 次。

### C：讀懂了，但 schema 沒地方放

- **讀題合約現在怎麼描述使用者的資料：**
  - `has` 只是一串引用原話的字串（`contracts/capability_check.py:501`），沒有型別；

## 1. 共用原則

1. **AI 讀，程式判。** 模型只把使用者的話填進固定詞彙的欄位，並引用原話。是否可行、要不要問，都由程式比對 registry 決定。
2. **每個新欄位都有 `not_stated`。** 沒填不算錯；填了金標沒有的值才算錯（捏造）。
3. **不對稱的後果，這是本輪最重要的一條。** 新讀到的資訊可以：
   - 補上 credit 或設定值；
   - 讓程式改成**提問確認**。

   但**單靠新讀到的資訊，不能直接拒絕**。拒絕仍然只能來自已驗證的合約理由（兩層理由規則）。這一條直接針對 2a 的失敗機制。
4. **新讀取用獨立的小呼叫，不改首輪讀題。** 首輪的 prompt 一個字都不動。依據：
   - prompt 變長會讓其他欄位變差（Logs 229-233，case 2 從 10/10 掉到 1/10）；
   - 把額外說明給 mini 看，會讓它偏向拒絕（ROUND-14）。
5. **說明文字寫一次、不調措辭。** 門檻不過就撤回，不做第二版。
6. **不加人工詞表。** 候選只來自 registry 本身與使用者原話。D3、2a 都證明了詞表不能類推。
7. **測試從簡**：先離線重放，live 最多 20 個受影響的 session、每個跑 1 次，跑之前先公告。

## 3. C1：使用者資料的種類（建議先做）

### 3.1 新的小呼叫：資料項目讀取

- **輸入：** 請求原文，以及首輪讀到的 `has` 引用。
- **輸出：** 每個 `has` 引用各一筆，扁平、必填：

| 欄位 | 值 |
|---|---|
| `quote` | 原話，程式核對要逐字出現在請求中 |
| `content` | `gene_expression`／`coexpression`／`regulator_gene_network`／`gene_gene_network`／`somatic_mutation`／`multi_omic_continuous`／`other`／**`not_stated`** |
| `made_by` | registry 的 workflow id／`outside`（原始資料或其他工具）／**`not_stated`** |
| `certainty` | `stated`／`unsure`（使用者自己說不確定） |

- **詞彙的來源：**
  - `content` 由 `accepted_input_modalities` 加上 `input_network` 的種類組成，不是人工詞表；
  - `made_by` 由 registry 的 workflow 清單產生。

### 3.2 程式怎麼用

| 讀取結果 | 程式的處理 |
|---|---|
| `not_stated` | **和現在完全一樣。** 不新增提問，不改變判斷 |
| `unsure`，而且這份資料是 credit 的 workflow 的必要輸入 | 改成提問確認，引用使用者原話（R12、R25 這類） |
| `stated`，內容不在 credit 的 workflow 的 `accepted_input_modalities` 裡，而且使用者沒有其他資料可以填這個 slot | **先問確認，不直接拒絕**（第 1 節第 3 條）。確認句引用 registry 的 `handoff_contract` 和使用者原話 |
| `stated`，內容符合 | 不改變判斷，只記錄 |

是否在之後的回合（使用者確認之後）才允許拒絕，屬於 P3 TaskState 的既有流程，本輪不改。

## 4. B1：設定連結（2a′）

### 4.1 和 2a 的差別

**完全以 2a 的失敗機制為依據。** 起點是 2a 的分支 `round26-settings-links`（`45022b15`），旗標維持獨立。

| 2a 的失敗 | B1 的結構改法 |
|---|---|
| Q45、Q14、P01：連到「沒被 credit 的 workflow」的設定，變成「X has no setting」 | 候選**只限於 credit 的 workflow 自己的設定**。連到候選以外的設定時，直接丟掉，不變成限制 |
| 新連結直接產生限制與拒絕 | **新連結不能產生限制。** 如果新連到的值違反合約（例如 sparsify 時 delta 超過 1/3），改成提問確認；只有首輪讀題的連結可以照舊拒絕 |

| U20：「not confirmed whether sparsify」被讀成關閉 | 原話是不確定時，值填 `not_stated`，交給提問確認 |

### 4.2 要誠實寫下的一點

上面的改法是**看過 2a 在開發題組上的結果之後才挑的**。2a 的 RESULTS 明說這種改法不能在 2a 那一輪做。

所以 B1 是新的一輪、新的宣告：

- **只有 h10 的結果，才能寫成能類推的改善。**

## 5. B2：結果連結（2b，選做）
