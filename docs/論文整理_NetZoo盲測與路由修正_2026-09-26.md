## 1. 摘要

本工作階段以 10 題中英雙語盲測檢驗 NetZoo agent 的三項能力：

1. 從不直接說出意圖的需求中推論出正確工具；
2. 需求不明確時，依各演算法的邏輯哲學判斷輸入與輸出；
3. 有 2～3 個工具可用時，以實驗假設區分它們並給出推薦。

一開始，使用者實測 Case 3（BONOBO）與 Case 4（LIONESS-PANDA）的 6 次 trial **全部失敗（0/6）**。
之後依「量測 → 事前宣告 → 逐字套用 → 實跑 → 結果紀錄」的紀律，共處理了 **20 個以上可追溯的成因**。
最後一輪完整盲測後，又逐題修正剩下的問題。

主要結果：

- **執行權限不變量從未被破壞**：所有實跑中，授權外洩（`should_execute=True` 或 `action≠no_tool`）皆為 **0**。
- **三組方法平手的實驗條件推薦**：有事實的 19 次推薦 **19 次正確、0 次錯誤**；沒有事實時的推薦 **0 次**。
  每一條引用都經人工判讀。
- **完整盲測（Log 179，英文 30 次）**：正確 20、部分 5、fallback 5、**判錯 0**。
  之後逐題修正：
  - Case 1 GIRAFFE：1/3 → **3/3**
  - Case 7 DRAGON：0/3 → **2/3**
  - Case 5 PUMA：0/3 → **2/3** 依內容推薦
  - 中文 Case 3：崩潰 → **3/3 正確**
- **測試套件**：2079 → **2178** 項，每一次套用都是 0 failed。
  prompt／schema 指紋（legacy `1f68bfde4081`、claims `348a144cd9b4`）**全程未變**，
  代表所有修正都在「契約形狀」與「確定性程式」層，沒有改 prompt 措辭。

## 2. 研究方法：為什麼這套流程能產生可信的結論

### 2.1 研究紀錄紀律（每一個修正都走完）

| 步驟 | 內容 | 目的 |
| --- | --- | --- |
| 1. 重放（replay） | 用 traced harness 錄下原始 provider I/O，離線重建失敗的每一步 | 從證據歸因，不從 issue 字串猜 |
| 2. worktree 量測 | 在隔離的 git worktree 實作並量測 | 主 repo 在宣告前不被改動 |
| 3. 事前宣告 | 寫下判準、撤回條件、已知風險，**之後不得修改** | 防止事後合理化 |
| 4. 候選 patch | 存成 `logNNN_candidate.patch`，**逐字**套用 | 宣告與實作一致可驗證 |
| 5. 離線判準 | 全套測試、確定性網格、指紋、重放 | 證明「只改了宣告的範圍」 |
| 6. 實跑 | gpt-4o-mini traced 實跑 | 描述性觀察，不作比率主張 |
| 7. 結果紀錄 | 逐條對帳判準；觸發撤回條件就撤回 | 負面結果同樣記錄 |

### 2.2 確定性網格（grid）：量「改了什麼」而不是「看起來好了」

每次修改都重算五個網格，並與基線逐位元組比對：

| 網格 | 規模 | 量的是什麼 |
| --- | --- | --- |
| Log 136 outcome grid | 15,273 個合法 outcome | 比對器對每種結構化需求的結果 |
| Log 148 evidence grid | 22,491 列 | 帶 explicit 證據時的比對 |
| Log 170 guidance grid | 9,996 列 | guidance／execute 模式的比對 |
| Log 174 tag grid | 所有 outcome × 已註冊 tag | tag 鑑別行為 |
| Log 150 pair grid | 6,000＋2,000 組雙讀法 | 多 hypothesis 的比對 |
| Log 143 validation grid | 15,273 個 outcome | 驗證器在省略 entity 證據時的反應 |

這些網格讓每一次「放寬」都能被精確計數。例如 Log 184 的放寬恰好是 252 個 outcome，
新增問題為 0。也讓「只改回覆、不改路由」的修改能被證明：五個網格逐位元組相同。

### 2.3 兩條刻意的限制

- **禁止以 prompt 措辭作為修正手段**：先前有六次失敗與一次撤回的 A/B 實驗。修正只能改契約形狀或確定性程式。
  指紋全程不變，就是這條限制的客觀證據。
- **不作比率主張**：連續的實跑共享漂移中的 provider 狀態，不是獨立樣本。
  同一份程式碼在語料上的通過數本身就會浮動 3～4 題。
  因此每個成因的**證據都是離線重建**；實跑只是描述性觀察。

| --- | --- | --- |
| 137 | 修正 2b（註冊表新增 `prefer_when`）**撤回** | 撞到釘住的 schema 雜湊測試，而宣告中沒有列為預期修改 |

## 3. 系統背景（論文中需要的最小描述）

路由管線：

1. 語意解讀（LLM 產生 `outcome_hypotheses`，每個欄位要附 `explicit`／`inferred` 證據與原文引文）；
2. 驗證（引文必須在原文中接地；本體一致性）；
3. review 修補（最多 2 次嘗試）；
4. 比對註冊表（12 個 netZooPy 工作流程）；
5. tag／LLM discriminator；
6. intent router；
7. 平手時的實驗條件推薦（Log 139 起）；
8. 資料夾內容檢查（Log 154 起）；
9. 確定性回覆渲染。

**只有 `exact` 且在 execute 模式下才會執行**；`fallback`、`ambiguous`、guidance 永不執行。

## 5. 問題與解決（依主題）

每個主題依序寫：**症狀 → 如何查證 → 修正 → 為什麼有效 → 量化證據**。

### 5.1 本體與能力宣告的矛盾：`sample` 是軸，不是節點（Log 136～137、172～173、176～177）

**症狀**：Case 3 的正確讀法（共表現網路、每個樣本一張）被判 `unsupported`，沒有任何候選。

**查證**：
- 本體允許 `coexpression_network` 的實體為 {gene, sample}；
- 但能力比對只接受 {gene}；
- 模型把輸入矩陣的樣本軸寫進了網路實體。

**修正**：
- Log 136：sample_specific 時，`sample` 視為 granularity 軸。
- Log 172：延伸到任何粒度的軸 artifact（成因 J）。
- Log 176：驗證器的蘊含改用與比對相同的判準（成因 K）。

**為什麼有效**：「一個樣本一張網路」的 sample 就是粒度本身，不是網路的節點類型。
修正沒有動任何能力宣告，所以不會讓錯的工具進來。

**證據**：

| 項目 | 數據 |
| --- | --- |
| 改變的網格 outcome | 580 個，全部為 `sample_specific`＋`sample`，違反 0 |
| 新解析出的 outcome | 26 個，全部科學上正確（TF-only → LIONESS-PANDA，含 miRNA → LIONESS-PUMA） |
| 中性路徑 Case 3 | 3/3 無候選 → **3/3** 正確平手 {LIONESS-coexp, BONOBO} |
| 驗證網格（Log 143 的 V2／V3） | 移除 `sample` 1,395 筆、`gene` 90 筆；新增問題 **0** |

### 5.2 澄清問題問錯了維度（Log 136 修正 2a）

**症狀**：outcome 已指定 artifact 與粒度，系統卻反問「What artifact should NetZoo produce?」。

**修正**：已解析、且所有候選都支援的維度不再成為澄清問題。

**為什麼有效**：planner 的資訊增益把「候選宣告上的差異」誤當成「使用者需要回答的差異」。
移除已解析的維度後，真正區分方法的「演算法假設」才浮上來。

**證據**：planner 改變 19 筆，其中 18 筆移到 `algorithm` 維度；改變已解析結果 0。

### 5.3 平手時用「實驗條件」而非「方法 tag」推薦（Log 139～142、167～177）

**症狀**：使用者原句已經包含區分事實（例如「a handful of patients」「which connections are trustworthy」），
系統卻用方法術語反問使用者。

**關鍵洞察**：
- 模型填 `selection_tags` 的比例只有 **4%**（1,275 次試驗中 51 次）；
- 被填的全是「重述題目主題」的 tag；
- **每一個真正能區分方法的 tag 都是 0 次**（例如 `tfa` 0/1275）。

換句話說，要模型挑「方法名詞」行不通，要改讓它引用「實驗事實」。

**修正**：
- 註冊表為每個方法宣告 `prefer_when` 實驗條件軸，例如 `cohort_size:few`、`per_edge_confidence:needed`、
  `covariates:yes`、`tf_activity_vs_expression:yes`；
- 平手時，模型只抽取「原文引文＋條件值」；
- 由程式驗證引文接地後決定推薦。推薦是**顧問性**的，永不改變執行權限；
- 回覆分兩種：A 版有引用事實時推薦，B 版沒有事實時列出各條件讓使用者選。

**為什麼有效**：
- 模型做它擅長的事：找出原文中哪句話描述了哪個實驗條件；
- 程式做它必須負責的事：接地驗證、決定、保持權限不變；
- 條件軸由註冊表宣告，沒有任何工具名稱寫死在推薦邏輯裡。

**證據（累計，Log 177）**：

| 平手 | 有事實且推薦 | 正確 | 錯誤 | 無事實時誤推薦 |
| --- | ---: | ---: | ---: | ---: |
| BONOBO／LIONESS-coexp | 5 | 5 | 0 | 0 |
| PANDA／OTTER／GIRAFFE | 9 | 9 | 0 | 0 |
| COBRA／LIONESS-coexp | 5 | 5 | 0 | 0 |
| **合計** | **19** | **19** | **0** | **0** |

範例引用（人工判讀全部正確）：
- `compute_constraints:constrained` ←「the real network will be very large, so memory and runtime are a concern」→ OTTER
- `tf_activity_vs_expression:yes` ←「some regulators are more active in some samples even though their own expression barely changes」→ GIRAFFE
- `covariates:yes` ←「separate the co-expression that comes from the sequencing batch」→ COBRA

**限制**：「about 400 tumour samples」從未被對應到 `cohort_size:many`（0/3）。
模型能把「a handful」「six donors」對應到「少」，卻不能把數字對應到「多」。
使用者決定**不設數字門檻**，遇到這種情況改為詢問使用者（Log 149）。

### 5.4 帶實驗事實的長句在語意解讀失敗（Log 143～147）

**症狀**：有具體事實的 prompt 有 7/18 落到 `semantic_fallback`；沒有事實的 prompt 是 0/6。
**事實越多，越容易失敗**。

**查證**：失敗全部是「缺證據」：系統要求模型為「已由其他欄位決定的值」另外提供引文。

**修正（都是「蘊含不需重複證明」的延伸）**：
- V1：共表現網路上本體不合法的 role 證據隨 role 一起退場；
- V2／V3：`sample` 軸、以及唯一剩下的節點實體視為蘊含；
- V4（Log 146，**經使用者同意推翻 Log 04 的一部分**）：guidance 模式下 operation 不需引文。
  比對器在 guidance 模式本來就會先把 operation 抹成 unknown，**這個值從未被讀取**，
  要求為它引用等於要求證明一個不影響結果的值。

**為什麼有效**：這類放寬只移除「對不影響選擇的值的證明要求」，所以不可能讓選擇變錯。
每一條都有網格證明新增問題為 0。

**證據**：
- F1 fallback 3/6 → **0/3**；F2 fallback 4/6 → 3/3 → **0/3**；
- V4 在驗證網格放寬 4,215 筆，**全部**是 `missing_evidence:operation=*`，新增 0；
- 錄下的 13 次失敗重放後救回 11 次。

### 5.5 候選集合被不該生效的資訊擴大或縮小（Log 148～149、170～171、174～175）

三個同類成因，都是「某個值已被抹去或不應生效，卻透過另一條路重新影響候選」。

| 成因 | 症狀 | 修正 | 證據 |
| --- | --- | --- | --- |
| F（Log 148） | granularity 證據標成 `inferred`，explicit 分支把只能 aggregate 的 COBRA 重新放入 | explicit 證據**只能縮小、不能擴大**候選 | 帶證據網格 656 列改變、擴大 **0**；F2 三候選 → 3/3 兩候選並到達推薦階段 |
| I（Log 170） | guidance 抹掉 operation，operation **證據**卻仍排除 COBRA | 抹掉值時連同其證據一起移除 | 「要分離批次效應」：6/6 錯判 LIONESS → **3/3 COBRA** |
| tag 偏向（Log 174） | 「重述主題」的 tag（如 `coexpression`）替使用者選了方法 | 重述已確定欄位的 tag 不參與鑑別 | 方法 tag 的網格列 0 改變；T2-none 恢復為平手並詢問 |

**為什麼有效**：三者共同的原則是「**候選只能被使用者真正表達的資訊縮小**」。

### 5.6 多種讀法：修補不再丟掉合法讀法（Log 150～159、164～165）

**症狀（Case 4）**：模型同時產生「每個樣本的調控網路」（合法）與「TF 活性矩陣」（粒度不合法）。
修補只修後者，並**丟掉**前者，結果變成錯誤的 exact GIRAFFE。

**修正鏈**：

| Log | 修正 | 原則 |
| --- | --- | --- |
| 150 | 修補保留未被修補的讀法；不同 artifact 的讀法保持為選擇 | 不同讀法是不同答案，不是一個答案加一個備胎 |
| 156 | 最後一次驗證後，保留單獨合法的讀法、移除仍不合法者 | 留下的每個讀法都通過**未修改的**驗證器，沒有放寬 |
| 158 | 修補回覆本身格式錯誤時，改用第一輪中已合法的讀法 | 延伸 Log 28「保留已驗證的第一次結果」 |
| 164 | 修補不得撤回「值沒變、引文仍接地」的引用 | 修補不應讓已成立的證明消失 |

**為什麼有效**：全部都只保留「模型自己寫出、且已通過驗證」的內容，**不發明任何值**。

**證據（同一句 Case 4 prompt 的結構計數，非比率）**：

| Log | fallback |
| --- | --- |
| 154 | 3/6（揭露 C1 回歸與成因 G） |
| 156 | 1/6 |
| 158 | **0/6** |
| 164 | **0/6**（6/6 exact LIONESS-PANDA） |

離線重放：多讀法的 fallback 3/3 救回，單一讀法 0/13 受影響；76 個修補重算後，合法變不合法 0。

### 5.7 以資料夾「內容」而非「檔名」判斷（Log 152～155、186～189）

**症狀**：Case 4 的資料夾裡沒有 miRNA 清單，系統卻反問「TF 還是 miRNA？」。

**演進**：

1. Log 152 先依檔名判斷。
2. 使用者指出：「不能只看檔名……萬一檔名不對但是內容對怎麼辦？」
3. Log 154 改為：每個候選只有在資料夾中某種檔案分配能通過**該工作流程自己的內容驗證器**
   （與執行前 preflight 相同）時，才算「具備」。檔名只決定先試哪個分配。

**延伸**：

- **Log 186（Case 5 PUMA）**：資料夾有 miRNA 清單時，PANDA 與 PUMA 都「具備」，內容無法區分。
  新訊號：先驗表的 regulator 欄含有被驗證為 miRNA 清單的名字，而且 TF-only 對應工具在排除這份先驗後無法具備，
  也就是沒有另一份乾淨的 TF 先驗。
  - 第一版沒有「乾淨 TF 先驗」條件，重放發現使用者原始 Case 4（`data/lioness-toy/` 同時有兩種先驗）
    會被錯誤推薦 LIONESS-PUMA；加上條件後改正，並用測試守住。

## 7. 為什麼這些修正能成功：可寫進論文的設計原則

1. **LLM 負責抽取，程式負責決定。**
   模型只回答「原文哪句話支持哪個值」；接地驗證、候選篩選、推薦與執行權限都由確定性程式負責。
   實驗條件推薦 19/19 正確，而且無事實時 0 次誤推薦，就是這個分工的結果。
2. **每一次放寬都附上「為什麼接受的東西本來就該接受」的論證。**
   反覆出現的論證有四類：
   - 被其他欄位蘊含的值（Log 25、143、184）；
   - 從未被讀取的值（Log 145／146 的 operation）；
   - 每段本來就能單獨接地的引文（Log 182）；
   - 只保留模型已通過驗證的內容（Log 150、156、158）。
   網格把每一類的影響範圍精確計數，新增問題皆為 0。
3. **候選只能被使用者真正表達的資訊縮小**（成因 F、I、tag 偏向）。
4. **顧問與權限分離**：推薦、內容檢查、資料夾發現都不改變 `action`、`should_execute`、
   `capability_match_status`、`matched_actions`，所以擴充這些功能不會增加誤執行風險。
   全程 0 外洩。
5. **內容優先於名稱**：路徑名、檔名都可能說謊（Case 3 路徑名洩漏、`blind-tests/case-1` 檔名對調）；
   以工作流程自己的驗證器判斷內容，判斷結果與實際能否執行一致。
6. **先重放再歸因**：traced harness 錄下原始 provider I/O；Log 182 用它推翻了 Log 179 的錯誤歸因。
7. **禁止 prompt 措辭修正**：強迫修正落在可測、可重現的契約與程式層。
   指紋全程不變，證明結果不是靠調 prompt 得來的。

## 9. 效度威脅（論文必須誠實寫出）

1. **樣本不獨立、數量小**：每題通常 3 次實跑，連續輪次共享 provider 狀態。所有實跑數字只能作描述，
   結論的證據是離線重放與確定性網格。
2. **單一模型**：全部以 gpt-4o-mini 量測，未在其他模型上驗證（gpt-4o 需另行授權）。
3. **測試與修正由同一團隊設計**：可能對這 10 題過度擬合。緩解方式：
   - 每個修正都以涵蓋整個本體的網格證明影響範圍；
   - 以 T1／T2／F 系列等非盲測句子另外實跑；
   - 事前宣告撤回條件。
4. **fixture 本身的缺陷**：路徑名與檔名洩漏（已修正），以及 `blind-tests/case-1` 檔名對調（Log 189 才發現）。
   早期盲測結果應據此解讀。
5. **並行修改**：工作階段後段，同一工作目錄有另一個 session 修改 `desktop/`、`server/`、`cli/slash_commands.py`。
   它造成主 repo 一項 golden transcript 測試失敗；本研究的所有判準都在只含 HEAD＋候選 patch 的 worktree 中量測。
