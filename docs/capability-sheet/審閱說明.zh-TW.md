# 能力表草稿 1：審閱說明（2026-10-08）

能力表本體在 `capability_sheet.draft.yaml`。它是英文，因為裡面的句子會直接出現在回覆裡。本文件用中文說明這張表怎麼用、哪裡需要你決定。

## 1. 三條規則

1. **「能產出」採封閉世界。** 只有 `produces` 裡有一條能交付使用者要的結果，才算支援。不在表上就算不支援。
2. **「不能產出」不參與判斷。** `near_misses` 只用來在回覆裡講清楚「為什麼這個看起來很像的方法不行」。它不需要列完整；漏列只會讓回覆少一句解釋，不會讓判斷出錯。
3. **`with_step` 算支援，但回覆必須說出那一步要你自己做。** 例如 LIONESS 本身不做存活分析，但它的每樣本網路可以放進 Cox 模型。這類情況要回答「可以，用 X 得到材料，之後的 Y 在 NetZoo 外做」，不能說「做不到」。這條規則就是要守住對照題上「誤說做不到」= 0。

每一條都附上出處，共三種：

| 標記 | 意思 |
|---|---|
| 論文 | 方法原始論文 |
| [EXEC] | 執行器實際寫出檔案的那行程式碼，2026-10-08 由子代理盤點並由我抽查 |
| [REG] | registry 裡在先前 Log 已驗證過的句子 |

## 2. 盤點時發現：registry 現有兩處講了執行器不會產出的東西

這兩處正是你擔心的「功能瞎掰」，只是來源是我們自己寫的模板，不是模型。

| 位置 | 現在的說法 | 實際情況 |
|---|---|---|
| `DOWNSTREAM_ANALYSES["run_dragon"]` | 「filter edges by the adjusted p-values」 | DRAGON 執行器只寫偏相關和 precision，從不呼叫 p-value 估計（`execution.py:792-800`） |
| `WORKFLOW_PRACTICAL_NOTES`、`_POINTS`、`DOWNSTREAM_ANALYSES` 的 `run_condor` | 「gives each node a core score」 | CONDOR 執行器只寫社群歸屬，沒有呼叫 condorQscore（`docker/run-condor:137-163`） |

每處有兩種修法，請選一種：

- **(a) 改文字：** 說明這些值需要另外算。
- **(b) 補執行器：** DRAGON 加上 p-value 估計；CONDOR 加上 core score 輸出。

另外，「targeting score／out-degree」整個 agent 都沒有計算。表上已標為 `with_step`。

## 4. 回答你的三個問題

### Q1：「不能產出」會不會太廣泛？

會，所以它不拿來做判斷（規則 1、2）。

做不到的事是無限多的，列不完。判斷只看「能產出」這份封閉清單，「能產出」是有限的、可以審完的，目前共 29 條。「不能產出」只保留容易誤會的近似項，目前共 34 條，用途是讓回覆講得精確。

### Q2：系統現在能不能理解使用者真正想產出什麼？

能找到「想要什麼」的那句話，但歸類錯誤。這是 Log 385 的 trace 資料（`study_purpose_detected`）。

**找到目標句：** U／N 共 45 次，42 次模型引用的原文正是使用者要的結果，例如「which splicing factors control inclusion of each alternative exon」「estimate the cell-type proportions within each spot」。U8 代謝通量 3 次全部沒抓到。

**歸類：** 詞彙裡有對應類別的才歸對，只有因果和預測兩類。其他全被塞進最近的類別：

| 題目 | 被歸成 |
|---|---|
| 剪接、de novo motif、ceRNA | regulator_change |
| 空間反摺積、擬時序、差異表現 | group_difference |

所以瓶頸不在「理解」，而在「只能從固定選項裡挑一個、而且沒有『都不是』」。新設計保留模型引用的原文，但不要它挑最近的類別。它要對每個候選條目做是非判斷：「這一條的結果能不能交付這句話？能／部分／不能」。「都不能」是正常答案，不是失敗。

### Q3：逐項檢查會不會漏寫需求，或沒理解意圖？

會，而且 baseline 已經看得到：

- **整個漏掉：** U8 一句都沒抓到。
- **只抓一半：** U3 只抓到「branch point」，漏了「pseudotime ordering」；U5 漏了 fold change 和 volcano plot。

漏寫的危險在於：漏掉的正好是做不到的那一項時，剩下的都能做，又會變回瞎掰。我提議用三道防線：

1. **覆蓋檢查（code）：** 請求中每個問句和每個「we want／need／how」子句，都必須被某條需求的引文覆蓋，或被明確標成背景（資料描述）。沒覆蓋到的子句不能默默略過，視為「未判斷的需求」，回覆要說「X 這部分我沒有判斷是否支援」。
2. **把理解攤開給使用者看：** 回覆第一段列出「我理解你要：1. … 2. …」，每項標上支援、需外部步驟或不支援。理解錯了，使用者一眼就能更正。這比追求模型百分之百理解更可靠。
3. **量測：** 下一組全新陷阱題的標註要加上「需求漏寫」這一欄，和瞎掰率一起看。

已知的限制：如果模型把一句話理解成另一個意思，而且引文本身是對的，code 檢查不出來。這只能靠第 2 道（讓使用者看見）和量測來抓。先前的 Log 也一再顯示，讀取層的召回率有上限（Log 383-384）。
