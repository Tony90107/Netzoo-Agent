## 1. 目標

三個科學目標不變：

1. 做不到的，不說成做得到；
2. 做得到的，不說成做不到；
3. 模糊的，一定追問。

本方向的具體目標：

- **減少誤承諾**，主要是參數組合、數量上限、清單外要求、明說沒有的資料。
- **不增加誤拒和該問沒問**：意圖理解與追問完全沿用現行系統，合約檢查只在放行前介入。
- 回覆改為「不能做附合約原文」，並提供選項卡。

非目標：

- 不改現行系統的意圖理解、路由與追問。
- 不用精簡讀取的 A1（要什麼結果）做任何判定。
- 不改 prompt 措辭來誘導行為。

## 2. 流程

```
使用者原文
 → 現行系統（不變）：理解意圖、選 workflow、追問
 → 現行系統判定「可以做」（core.kind = DO，或準備執行）時：
     → 合約檢查層（新）
        候選 = 現行系統選定的 workflow（不用精簡讀取的 A1 重選）
        精簡讀取只讀這些 workflow 的：設定（B5）、數量（B6）、workflow 專屬條件（B4）、
        禁止條件（C1–C7）、額外要求的合約核對（D4）
     → 有「附合約原文」的違反 → 改判不能做（或部分可做）＋原因＋最接近、可以做的選項
     → 有會改變能不能做的數量或條件疑問 → 加一題追問（和現行系統的回覆同一輪）
     → 都沒有 → 照現行系統的判定
 → 回覆：不能做時用「不能做附原文」模板；可以做時附上揭露事項，執行前列出要確認的項目
```

## 3. 合約檢查層

### 3.1 讀什麼

精簡讀取的第 1 步（核心讀取）和第 3 步（聚焦讀取）保留，但：

- **候選 workflow 由現行系統決定**：現行系統放行了哪幾個 workflow，就只檢查哪幾個。
- **第 3 步只讀「限制類」欄位**：B4、B5、B6，以及這些 workflow 的必要設定（例如 BONOBO 的 log 轉換與中心化）。不讀 B1–B3 的意圖欄位，那是現行系統的工作。
- C 類禁止條件（C1–C7）沿用第 1 步：使用者有提才填，需附原文。
- D4 額外要求沿用合約核對：met 或 contradicted 都要附合約原文，程式逐字核對。

### 3.2 預設值（使用者 2026-10-19 決定）

- 突變來源預設體細胞，數值型態預設連續值，並揭露；
- 同一批樣本、網路種類交給輸入檢查；
- 使用者表示不確定時才問；
- BONOBO 的 log 轉換與中心化仍必須宣告。

### 3.3 只有附合約原文的違反才能否決

| 情況 | 能不能否決 |
|---|---|
| C1–C7 成立：清單外結果、清單外主張、對外動作、資料形式特殊狀況、未註冊方法、明說沒有的必要資料、合約寫明不支援的設定或數值 | **可以**：必須有使用者原文＋合約原文（或 sheet 的 near-miss 條目），兩者都經程式逐字核對 |
| B5 設定違反合約範圍或組合（例如只給 lambda1、lam = 1.5） | **可以**：附 control 的定義與合約原文 |
| B6 數量超過合約上限（例如 LIONESS-DRAGON 數值上限、COBRA 基因數少於樣本數） | **可以**：附算式與合約原文 |
| D4 合約寫明做不到 | **可以** |
| 「找不到符合的結果」這類由讀取推出來的拒絕（narrowing） | **不可以**：這是精簡讀取 A1 的弱點，交回現行系統 |
| 精簡讀取讀出「不確定」 | **不否決**；只有在不同值會讓同一個 workflow 從可做變成不可做時，才加一題追問 |

### 3.4 已知的程式漏洞（h3 找到，混合方向會用到，必須修）

- **L40**：數量不確定時，要填「單一資料種類的特徵數」，COBRA 的基因數條件才能判斷。
- **L29**：C 類一旦成立，就直接不能做，不再追問 B4。
- **L28、L02**：B5 的「不確定」只收使用者原文裡出現的值，不能把整個允許範圍列進去；否則會跳過組合檢查，或多問一題。

### 3.5 舊的混合閘門

h2 的混合閘門（`hybrid_gate_call.py`）用的是舊讀取，淨效果 −1。依使用者 2026-10-19 的決定，它預設關閉，由本 spec 的合約檢查層取代：沿用同一個接入點，即現行系統 core.kind = DO 時。

## 4. 回覆

- **不能做**：開頭直接寫 NetZoo 不能做什麼、為什麼（附合約原文），接著列最接近、可以做的選項。沿用 `2721d970` 的英文模板。
- **可以做**：
  - 現行系統的判定不變；
  - 附上 20 項科學解讀選擇中適用的揭露事項，例如「λ 由資料估計」「PUMA 的 miRNA 邊不使用 miRNA 表現量」，由模板產生；
  - 第 1–5 項「必須確認」中被觸發的項目（例如提到分組時，LIONESS 的背景 cohort），列在執行前的確認中。
- **選項卡**：把現行系統的候選 workflow 轉成選項卡，最多 3 個，依符合度排序，不可行的另列並附原因。這是第二步的工作，排在合約檢查層之後。

## 5. 驗收

### 5.1 用同一批現行系統輸出評估否決層

合約檢查層是加在現行系統判定之後的一層，所以：

1. 新的英文盲寫題組 h4（約 48 題，寫題者沒看過 h1–h3、56 題與本設計）先跑一次現行系統；
2. 在**同一批 session 的判定**上，離線套用合約檢查層，得到「現行＋否決」。

這樣兩組的差異只來自否決層，不會混入現行系統每次跑的變動（h2 同程式兩次有 14–17 題不同）。

另外做一次接上 live 的煙霧測試（少量 session），確認接線正確。

### 5.2 指標與採用門檻（凍結於 h4 的 ROUND.md）

| 指標 | 採用條件 |
|---|---|
| 誤承諾（含部分承諾） | **現行＋否決 < 現行** |
| 誤拒 | 現行＋否決 ≤ 現行 |
| 該問沒問 | 現行＋否決 ≤ 現行 |
| 嚴格分數 | 現行＋否決 ≥ 現行 |

另外報告：
- 每次否決的理由與原文是否正確（盲標）；
- 「能跑但科學意義不同」的題數；
- 揭露與執行前確認觸發的次數。

### 5.3 成本

- h4 現行系統 48 個 session：nemotron 免費額度＋gpt-4o-mini，約 US$0.1。
- 合約檢查層的讀取約 US$0.03。
- 每次執行前都先報備。

## 7. 風險

- **否決層讀錯，造成誤拒**：限制只有附原文的違反才能否決，並由程式逐字核對。h4 會專門統計否決的對錯。
- **同一題多一次讀取**：只在現行系統判定可以做時才跑，而且只讀限制類欄位。
- **兩個系統的說法不一致**：否決後的回覆由模板產生，不保留現行系統原本「可以做」的文字。
